# Как участвовать в разработке

Этот файл действует во всех репозиториях организации LDS. Правила конкретного проекта, если
они отличаются, описаны в его собственном `CONTRIBUTING.md` или `README.md` — они имеют приоритет.

Полные инженерные конвенции (стандарты кода, чек-листы ревью, конфиги линтеров) —
[ldslab/engineering-guidelines](https://github.com/ldslab/engineering-guidelines).
Репозиторий приватный и доступен участникам организации.

---

## Before you start

1. Прочитайте `README.md` и `CLAUDE.md` (если есть) репозитория — там устройство проекта и его
   особенности.
2. Существенные изменения согласуйте **до** реализации. Обсуждение архитектуры в готовом PR на
   тысячу строк заканчивается либо переделкой, либо аппрувом «лишь бы не переделывать».
3. Убедитесь, что задача не решается уже кем-то — посмотрите открытые PR.

## Branches

Работаем от `master`, ветка короткая и живёт до мержа:

```
<type>/<краткое-описание-через-дефисы>
```

`type` — `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`.

```
feat/tasks-department-assignment
fix/settlement-empty-slice
perf/schedule-n-plus-1
```

## Commits

[Conventional Commits](https://www.conventionalcommits.org/), на английском:

```
<type>(<scope>): краткое описание в императиве
```

- `scope` — модуль, а не слой: `fix(scanning):`, не `fix(controller):`.
- Заголовок до 72 символов, без точки в конце.
- Тело объясняет **зачем**. Что изменилось — видно в diff.
- Ломающее изменение: `!` после scope и секция `BREAKING CHANGE:` в теле.
- Мусорные коммиты (`wip`, `fix`, `.`) вычищаются перед PR через `git rebase -i`.

## Pull requests

- **PR должен читаться за 20 минут** — ориентир до ~400 изменённых строк. Крупную задачу режьте
  на несколько PR: способность находить дефекты резко падает после первой сотни строк.
- Заполните шаблон описания: зачем, что сделано, как проверить, риски.
- До запроса ревью прогоните тесты и линтер локально и перечитайте свой diff целиком.
- Мержим squash-мержем; ветка удаляется автоматически.

PR принимается, когда: зелёный CI, есть аппрув владельца кода, закрыты все обсуждения, ветка
обновлена относительно `master`.

## Review

- Ревью начинается в течение рабочего дня. Не успеваете — скажите сразу и передайте другому.
- Помечайте вес замечания: `blocking:`, `nit:`, `question:`, `praise:`.
- Обсуждаем код, а не автора. Замечание без объяснения — плохое замечание.
- Тред закрывает тот, кто его открыл, а не автор PR.

## Quality gates

- Тесты и линтеры — обязательные проверки PR, а не рекомендация.
- Красный `master` чинится первым приоритетом: пока он красный, никто не может отличить свою
  поломку от чужой.
- Каждый исправленный дефект закрывается тестом, который падал бы до исправления.

## Что не коммитим

- Секреты, токены, пароли, дампы с персональными данными. Секрет, попавший в git, считается
  скомпрометированным и **ротируется** — удаления коммита недостаточно.
- Артефакты сборки, зависимости, локальные настройки IDE.
- Закомментированный код — он есть в истории git, и только там ему место.
